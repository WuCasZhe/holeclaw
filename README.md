# HoleClaw

HoleClaw 是一个树洞Claw，它可以按时间范围、评论数和收藏数阈值读取帖子，并生成报告，既可以作为 Codex Skill 使用，也可以在命令行中手动执行。

## 工作方式

```text
用户登录的浏览器
        │
        ▼
北大树洞列表/详情接口
        │
        ▼
带随机令牌的 127.0.0.1 回调
        ├── SQLite 本地缓存
        ├── JSON 检查点
        └── Markdown 报告
```
登录状态保存在当前工作目录的 `.auth/`。

## 环境要求

| 依赖 | 说明 |
|------|------|
| Python 3.10+ | 运行采集脚本 |

| Google Chrome / Edge | 浏览器自动化 |

## 安装

作为 Codex Skill 安装：

`推荐直接在 Codex 中发送消息，让内置技能安装器完成安装`

只使用独立自动化时，可克隆到任意固定目录：

```bash
git clone https://github.com/WuCasZhe/holeclaw.git
cd holeclaw
python3 scripts/run_digest.py standalone --help
```

## 归档进度与写入频率

`archive` 默认在有新进展时每 5 分钟输出一次进度，阶段结束或中断时补报剩余进展。可在归档命令后添加参数调整：

- `--progress-pages 0 --progress-seconds 300`：每 5 分钟输出（默认）。
- `--progress-pages 5 --progress-seconds 0`：每新增 5 个已提交列表页输出。
- `--progress-pages 5 --progress-seconds 300`：页数或时间任一条件满足即输出。

日志频率与数据库写入频率独立。列表默认每页提交，可用 `--cache-chunk-pages 5` 改为每 5 页提交；评论默认每 10 页或帖子结束时提交一批。增大写入批次会增加中断后需要重扫的未提交数据。续传检查点默认每 100 个列表页保存，并在结束或中断时保存。

## 缓存复用

热门报告与本地归档默认使用独立缓存。运行目录为 `${HOLECLAW_RUNTIME_DIR}`，未设置时为 `${CODEX_HOME:-$HOME/.codex}/holeclaw-runtime`：

```text
holeclaw-runtime/
├── holeclaw-cache-v5.sqlite3          # run / standalone 热门报告列表缓存
├── holeclaw-checkpoints-v4/           # 按任务参数区分的续传检查点
└── archives/<账号标签哈希>/
    ├── list-cache-v5.sqlite3          # archive 专用列表缓存
    ├── archive.sqlite3               # 归档正文、评论及图片元数据
    └── images/                       # 下载的图片
```

归档不会默认读取或更新报告列表库，不同账号的归档列表也相互隔离。`--cache` 可覆盖当前命令的主数据库，`archive --source-cache` 可显式覆盖归档列表缓存；自定义路径时需自行保持分离。

已有报告缓存、档案和已完成的固定日期归档继续可用。旧的未完成归档若使用原共享报告库，切换默认路径后会重新扫描列表，复用已保存的评论和图片，并保存新检查点；原报告库保持不变。显式指定 `--source-cache` 的任务仍按原路径续传。

归档按批查询评论和图片状态，跳过没有变化的帖子及归档成员写入。历史列表缓存保留原观察时间，不会因为复用而被标记为刚刚联网获取，也不会覆盖档案中更新的已知帖子字段。

部分候选已完成时，由本地直接登记这些帖子，只将需要补采评论、图片元数据或图片文件的候选交给浏览器。候选页号保持不变，已有检查点可继续使用；同一批共享图片文件只检查一次，文件缺失或大小不符时仍会补下载。

归档摘要默认不执行全库完整性扫描，JSON 中的 `cache_integrity` 为 `not_checked`。需要检查时，在原归档命令后添加 `--verify-cache`；完整性校验通过后该字段为 `ok`。已完成的固定日期归档也可使用此参数重新校验。

报告命令 `run`、`standalone` 同样支持 `--verify-cache`，默认跳过全库校验；直接复用缓存时也可显式校验。

## 超时、不可访问帖子与图片

远端请求和本地回调每次尝试最多 60 秒，图片流连续 30 秒没有数据会超时并重试。服务器指定的 `Retry-After` 等待时间完整保留，等待期间仍可中断。

归档遇到已删除或不可访问的帖子时，保存 `post_not_found` 状态并继续。摘要用 `unavailable_posts` 单独计数，不将其当作评论采集完成。相同评论数的后续归档可复用该状态；`--fresh` 可重新检查。

图片使用二进制上传，不经过 Base64 JSON。最多同时处理两张图片的下载、上传和落盘；服务端按 64 KiB 分块写入并计算哈希，文件同步不阻塞评论提交。单张图片仍限制为 20 MiB，失败上传清理临时文件，重试保持请求身份并校验内容一致。

## 离线搜索索引

支持 FTS5 trigram 的 SQLite 会在归档库首次打开时建立索引，旧数据只回填一次；后续正文变更在同一事务内维护索引。首次升级可能需要额外时间和磁盘空间。

`archive-search` 对至少三个字符的关键词使用索引，再验证原始子串匹配，保持大小写和中文匹配语义。一至两个字符的查询、尚未建立索引的旧库及不支持该索引的新建库继续使用原搜索方式。搜索命令本身保持只读，旧库可在下次执行 `archive` 时建立索引。

## 采集效率

- 零评论帖在准备批次中直接登记评论扫描完成，省去逐帖空评论回调；历史评论仍保留。
- 评论完成后释放帖子工作名额，图片进入独立队列。图片文件处理仍最多并行两张，图片准备阶段最多并行配置的请求并发数；列表按原页序等待整页完成后提交。
- 同页优先启动评论较多的帖子，评论数按 1000 条采集上限估算工作量。
- 缓存候选直接携带准备结果。详情发生变化或排队期间同一帖子已被处理时重新准备，避免复用过期游标。
- 图片引用未变化时跳过写入；下载计划按键分页读取，每帖最多缓冲 128 个引用，最多保留 64 个帖子的队列。
- 同时筛选评论和收藏且使用 `--match-mode all` 时，已不满足评论条件的帖子不再补查缺失收藏数。此类窗口的 `favorites_complete` 标为 false，后续需要收藏数完整覆盖的查询会重新扫描；不会把主动省略标记为接口不可用。`any` 和仅收藏筛选仍按原方式补查。

## 磁盘 I/O

- 相同评论正文、时间、署名和引用不重复更新。评论行的 `observed_at` 表示当前内容版本的观察时间；最新扫描时间由 `comment_scans.observed_at` 保存。
- 完整缓存命中的新归档直接登记本次成员，省去复制、删除候选正文。仍需补采时继续保存完整候选快照，保证续传读取原窗口数据。
- 已成功的图片请求重试只读取并校验完整内容哈希，不再创建临时文件或执行 `fsync`；新上传仍按原方式同步并原子发布。
- 检查点使用紧凑 JSON。同一进程内内容和文件状态都未变化时跳过重复保存；文件被修改或删除后会重新写入。
- 档案总数在事务内增量维护，旧库首次打开时回填一次；后续摘要不再为总数扫描评论库。
- 一次图片完整性检查可跨 500 帖批次复用文件状态，最多保留 4096 项。下一次检查重新读取文件状态，及时发现删除或大小变化。
